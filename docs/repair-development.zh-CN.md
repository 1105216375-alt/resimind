# 按失败结果增强：局部修复与原任务保持

后续已加入[日程构造与有限搜索](search-development.zh-CN.md)，并修正“床数等于住客容量”的检查假设。下文保留本阶段的历史结果；对应源码快照未改写。

**已实现数据绑定、可回滚的局部修复、原任务保持、计价修正及过夜状态保护。14/28 个旧候选改善了局部检查，但完整通过数未增加；最近一轮联网开发验收为 0/2。** 首轮曾出现 1/2 官方通过，复核发现该计划漏掉过夜闭环，因此增加更严格的检查并重新运行。最后又修正了字段补齐与检查清单的接入错误，仅做离线回归，没有另报新的联网成绩。所有结果均保留，不能据此宣称完成率提高或超过 NeSy。原先 12 题三组正式结果保留在[原报告](chinatravel-evaluation.zh-CN.md)。

## 修了什么，为什么修

| 实测发现 | 本次修改 | 当前边界 |
| --- | --- | --- |
| 首轮常见价格乘数量错误、路线端点错误；28 个候选仅 1 个环境合格 | 用精确实体名、运输 ID 查询官方沙盒，绑定价格、总费用及既定方式的路线 | 不猜未知餐馆，不模糊匹配，不擅自更换目的地 |
| 重写完整计划容易破坏已有正确内容 | 新增通用 `resimind.repair`：补丁带基础计划哈希、旧值、证据引用；完整复验后原子提交 | 只改善部分检查时是中间草稿；不算成功交付 |
| 原任务在后续候选中发生漂移 | 最终生成提示只保留 schema，明确原始需求并放在末尾；验收核对出发地、目的地、人数和天数 | 保留原生探索提示；尚未证明消除所有漂移 |
| 上游提示把 `cost` 描述为每人／每车／每房费用，与检查器的总价计算冲突 | 明确 `price` 是单价，`cost` 是按票数、人数、房间数或车数计算的总价 | 数字仍须工具查询及独立复算 |
| 空约束译码后仍重复改计划 | 先检查自译约束及公开任务标题；无效译码直接标记未完成 | 本轮没有实现自动重新翻译 |
| 金额公式正确也可能少买票、少订房 | 增加人数覆盖检查，按沙盒四人一车的假设核对车数 | 本地验收可以比官方计分更严格 |
| 官方通过的计划缺少晚餐后回酒店及实际过夜的记录 | 非末日最后一项必须是结束于 `24:00` 的住宿，才能确认次日路线起点；生成提示同步说明 | 不用改成“前晚餐厅→次日早餐”掩盖缺失住宿状态 |
| schema 补齐后增加了检查项，导致事务保守拒绝；缺字段反馈也不具体 | 相同活动结构保持同一检查清单，缺失值先记未知；反馈明确字段名称 | 不放宽事务层的检查一致性要求 |

旧记录中，初始 12 个计划都保持了公开任务的出发地、目的地、人数与天数；后续 16 个非空候选中有 **12 个发生元数据漂移**，第二轮 9 个里有 8 个变成了“北京→南京、1 人、2 天”。原始 API 响应已经如此，排除了 JSON 解析造成替换的解释。上游最终提示恰好包含这份示例；它可能影响了生成，但本轮没有隔离试验证明唯一因果。

通用修复 API 与模型厂商、ChinaTravel、LangGraph 无关，仍是纯 Python 零依赖。领域适配器提供证据和检查器，可用于其他结构化任务；本次只对出游适配器做了真实模型开发验收，没有把结果外推到数学或桥梁。

单独看共享的 **12 个首轮候选**，11 个改善了局部检查，官方完整通过仍为 **0→0**。没有挑后续最好的一版替代首轮。有效候选没有被改坏；此次最终允许交付的仍只有原本有效的那个候选。

## 两轮真实 DeepSeek 开发验收

保持同一 `deepseek-flash`、temperature 0、非思考模式和原有每题 128 次调用／600 秒上限。仍使用一个原生 ReAct 实例，最多 50 步、3 份模型候选，不为修订重置步数。每份候选最多保留 3 轮局部修复。

第一轮尚未加入过夜状态保护：

| 公开原题 | 官方结果 | 实际 API 调用 |
| --- | --- | ---: |
| 上海→苏州，2 人、3 天，轻松自由行 | 官方 schema／环境／金标准逻辑全部通过，第 3 个候选交付 | 105 |
| 上海→重庆，2 人、3 天，预算 4000、市内交通省时 | 2 个非空候选均未通过，达到 50 步后没有新候选，未交付 | 104 |

合计 **1/2 完成、0 次错误交付、1 题未完成**。实际 209 次模型调用，输入 5,971,713 tokens、输出 31,196 tokens，用量缺失 0；没有重试或替换失败样本。详细账本、候选、修复过程、终态及官方评分均在[证据归档](evidence/chinatravel-repair-v1/README.md)。

复核发现：苏州题第 3 个原始候选仍未通过；局部补丁只修改两个早餐路线的 6 个字段，将起点从酒店改成前一晚的餐馆，便通过了官方检查。计划只记了首日早晨短暂入住，没有明确晚餐后回酒店及过夜。这证明了候选层面的官方得分改善，也暴露了评分范围不完整，不能解释为现实行程已经正确。

因此新增过夜保护，并将原先的成功计划重新检查：现在返回 `unfinished`，没有交付，见[专门回归记录](evidence/chinatravel-repair-v1/overnight-regression.json)。随后冻结新版本，对同样两题完整重跑，没有挑选替换题目：

| 公开原题 | 最新版交付结果 | 实际 API 调用 |
| --- | --- | ---: |
| 上海→苏州，2 人、3 天 | 未完成，未交付 | 81 |
| 上海→重庆，2 人、3 天 | 未完成，未交付 | 104 |

最新一轮 **0/2 完成、0 次错误交付、2 题未完成**，185 次调用，输入 4,991,234 tokens、输出 27,720 tokens，用量缺失 0。两轮合计 394 次调用。旧版两轮开发验收的 ResiMind 都是 0/2，见[历史归档](evidence/chinatravel-development/README.md)；最新结果没有建立相对于旧版的完成率增益。

各轮重新采样了候选，同时改变了提示、数据绑定、局部修复及验收条件，**不是共享初始候选的消融对照**；两题也不足以估计泛化表现。不能把首轮 50% 与先前正式 12 题的 41.7% NeSy 成绩比较。本次观察到的任务元数据保持情况属于开发诊断，不是已经消除漂移的证明。

## 最后一次接口修正：不新增模型调用

第二轮 5 个非空候选都没有通过 schema。苏州候选遗漏了火车活动的 `start/end`；重庆候选还将出租车路段写成独立活动。进一步检查发现一个接入错误：工具补齐起终点后，检查器才新增数据绑定与人数检查，导致事务层判定检查清单改变而拒绝提交。

已修改适配器：对于同一活动结构，即使 schema 尚未通过，也保留这些检查项，缺值记为未知。事务核心仍要求修复前后检查名称一致、已通过项不退化；没有为了通过而放松门槛。同时补充了带长度限制的具体 schema 错误信息，例如缺少 `start` 或 `end`。

将最近一轮**全部 5 个真实非空候选**在隔离进程中重新修复，全部完成后才离线读取 gold：

| 指标 | 原始候选 | 最终代码修复后的草稿 |
| --- | ---: | ---: |
| 官方 schema 通过 | 0/5 | **3/5** |
| 官方环境通过 | 0/5 | 0/5 |
| 官方逻辑通过 | 5/5 | 5/5 |
| 官方完整通过 | 0/5 | **0/5** |

新增模型调用为 **0**，两个来源任务均没有新增可交付计划。这里证明的是字段修复通路已经打通，剩余环境问题仍未解决；不是一次新的端到端通过率。完整[配对结果](evidence/chinatravel-repair-v1/schema-refinement/report.json)与[回放脚本](../scripts/replay_repair_refinement.py)已公开。

## 验证与后续优先项

- 核心与原有领域测试 **791 项通过**：原有 716 项，加通用修复 75 项。
- 原始评测集成测试 **44 项通过**，最新版新增集成测试 **58 项通过**。原始集成检查包含真实 macOS 隔离检查，新增检查包含过夜缺口与真实缺字段候选回归；这些测试不调用模型。
- 离线回放的原始输入、完整补丁链、证据引用、源码和数据哈希复核一致；归档逐成员解压复核，原始正式记录未改写。
- 新模块只对明确检查的真假状态保证不退化；未编码的自然语言语义、检查器缺陷和数据可信度不由哈希或补丁事务证明。

下一步应优先补**约束指导的实体选择与时间安排**，并为修复预留生成预算。当前保守修复不会猜未知实体、补选交通方式或移动活动时间；这些剩余问题需要搜索或模型做决策。之后冻结新版本，选取未用于开发的新任务，运行共享首轮候选的“仅门控／普通反馈／结构化残差与局部修复”对照，才适合判断完成率和机制贡献。
